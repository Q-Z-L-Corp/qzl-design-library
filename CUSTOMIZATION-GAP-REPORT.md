# QZL Design Library — Cross-Platform Customization Gap Report

## Executive summary

The guiding principle is **Easy by default. Flexible by design. Extensible when needed.**

The source currently exports 50 component functions from `@qzlcorp/react` and 48 from the main `@qzlcorp/react-native` entry point. React Native also exposes `QrScanner` through its separate Expo subpath. These counts differ from the 45/44 figures in the audit request.

The library already has useful foundations: Web components commonly accept `className` and native HTML attributes; React Native components commonly accept `StyleProp` and a built-in light/dark `theme`; data components support formatters, per-series colors, and render callbacks where they matter. The largest gaps are concentrated in complex components rather than simple visual primitives:

1. **Carousel** originally hardcoded text navigation and dots; the additive customization API is implemented in this change.
2. **React Native theming** supports only the two built-in palettes; consumers cannot supply a semantic theme object.
3. **Dialog and sheets** hardcode their close controls and provide limited control over panel structure.
4. **DataTable** owns sorting state and has fewer header/empty-state composition options on React Native.
5. **React Native Select** is a custom disclosure list rather than a native picker and lacks filtering, outside dismissal, and a public open-state API.

Only the Carousel gap is implemented in this audit. The other proposals are recorded for prioritization; they should not be added without validating consumer use cases.

## Audit method and compatibility policy

Reviewed the public exports, component prop interfaces, rendered internals, and Web styles in both packages. The audit evaluates:

- **Level 1 — Configuration:** behavior, state, variants, sizes, and options.
- **Level 2 — Styling:** Web classes/HTML attributes and React Native styles/themes.
- **Level 3 — Composition:** children, structured data, and render callbacks.

All proposals below are additive candidates. Existing defaults and behavior should remain unchanged. No breaking changes are recommended. “No change” means the current API is sufficient for its scope or that an extension would add complexity without a demonstrated consumer need.

## Shared patterns and recommendations

- **Web styling:** `className` plus semantic CSS variables is the primary customization path. Most wrappers forward native HTML attributes. Tabs is a notable composite that does not currently expose a caller class.
- **React Native styling:** most components accept an outer `StyleProp`; some also expose `inputStyle` or `contentStyle`. Child controls are often inline-styled and cannot be individually styled without composition.
- **Theme model:** native components accept only the built-in `ThemeName` (`light` or `dark`). Web semantic CSS variables can be overridden by the consuming application. A shared, typed custom-theme mechanism would improve cross-platform branding but requires a deliberate theme provider/token contract; do not add an object-valued `theme` prop independently to every component.
- **Composition:** children work well for content surfaces and overlays; `DataTableColumn.render` and chart formatters/colors cover data-specific use cases. Render callbacks should be reserved for components with a clear internal control boundary, as in Carousel.
- **State:** simple input controls are mostly controlled; Accordion and Carousel support controlled and uncontrolled modes; DropdownMenu/Popover keep open state internal; DataTable sorting is internal. Maintain existing defaults and add controlled modes only for real integration needs.
- **Accessibility:** Web generally uses native elements and ARIA; native components use React Native roles/states. Platform differences such as native Select and Tooltip behavior should be explicit rather than hidden behind misleading parity.

## Carousel implementation

The implementation preserves existing behavior while adding:

- `navigation: 'text' | 'arrows' | 'none'`, defaulting to `'text'`.
- `pagination: 'dots' | 'progress' | 'fraction' | 'none'`, defaulting to `'dots'`.
- `navigationPlacement: 'below' | 'overlay'`, defaulting to `'below'`.
- `loop`, defaulting to `false`.
- `renderNavigation` and `renderPagination` callbacks for consumers who need fully custom controls. Each callback receives the current index, slide count, enabled-state booleans, and navigation actions; `goTo` throws a `RangeError` for an invalid index.
- The Web root exposes `className`; React Native retains outer `style` as its platform-level styling mechanism. Custom callbacks are the control-level composition mechanism.

Buttons remain native keyboard/touch controls, with stable accessible names regardless of visible arrow glyphs. Dots remain selectable and accessible. Progress/fraction indicators announce the current slide and count. Swipe gestures and arrow-key navigation of arbitrary slide content are not included: they can conflict with nested controls and are not required for accessible button-based navigation. Looping is opt-in and disabled by default.

## Implementation and migration status

The Carousel additions are additive, preserve the text/dots/below/non-looping defaults, and require no migration. Web and React Native builds and tests pass, and the generated API registry reflects the new declarations. Other candidates remain recommendations, not implicit commitments.
